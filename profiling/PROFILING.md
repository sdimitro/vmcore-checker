# Memory profiling: peak RSS of vmcore-checker

Goal: measure and reduce peak RSS of the binaries that run inside the
crash kernel, where the reserved crashkernel memory is scarce. The
number that matters most is the **TinyGo linux binaries'** peak RSS;
the stock Go build is profiled alongside because only it supports
pprof, and both compile the same source, so its allocation sites are
the same ones driving TinyGo's heap.

## TL;DR

Peak RSS on a 32 MiB kernel log went from **~84-118 MB to ~33 MB**
(tiny builds; input size + ~1 MB constant), and from ~92-98 MB to
~37 MB for stock builds. On the realistic 700 KB log the tiny binary
now peaks at **1.0-1.5 MB** (was ~3 MB). Wall time on 32 MiB dropped
from 0.33s to 0.02s as a side effect. Achieved by removing all
per-line allocations from `dmesgcrash.Parse` — peak is now just the
input buffer plus a small constant, confirmed by pprof showing
`os.readFileContents` as 94% of allocations with nothing else left.

## Environments

- linux-arm64: docker container (`profiling/Dockerfile`: ubuntu:24.04 +
  GNU time) on an Apple Silicon host — native arm64, no emulation.
- linux-amd64: a bare-metal Linux server (128 cores, 2 TiB RAM),
  reached over ssh as `$LINUX_BOX` below, scratch under
  `$SCRATCH/vmcheck-prof`.
- Compilers: Go 1.25.4 darwin/arm64 (cross), TinyGo 0.41.1 (LLVM 20).
- RSS = "Maximum resident set size" from GNU `time -v` (wait4 rusage).

## Inputs

Generated by `profiling/gen-input.sh` (regenerable, gitignored):
banner + cmdline up top, non-crash boot/runtime filler noise with
realistic `[ts] [Tn]` prefixes, and the golden-corpus
`arm64-nvidia-nullptr` crash (stack trace included) at the tail — the
worst realistic kdump case: a huge log whose crash region is at the end.

- `real-700k.txt` — a real 7132-line dmesg export (rcu_do_batch crash)
- `synth-1m.txt`, `synth-8m.txt`, `synth-32m.txt` — 32 MiB matches the
  practical upper bound for kernel `log_buf_len`
- `skiplist` — type-rip entries derived from the corpus `.expected`
  files, so runs exercise the full match + note-writing path

## Commands run (verbatim)

Instrumented builds (`-tags memprofile` adds `-memstats`/`-memprofile`
flags; never in release builds):

```sh
make profile-linux-arm64 profile-linux-amd64 tiny-profile-linux-arm64 tiny-profile-linux-amd64
```

Input generation:

```sh
profiling/gen-input.sh 1  profiling/inputs/synth-1m.txt
profiling/gen-input.sh 8  profiling/inputs/synth-8m.txt
profiling/gen-input.sh 32 profiling/inputs/synth-32m.txt
cp /path/to/a/real-dmesg-export.txt profiling/inputs/real-700k.txt
CORPUS=$(go list -m -f '{{.Dir}}' github.com/sdimitro/crashfp)/dmesgcrash/testdata/corpus
{ echo "# generated 2026-01-01T00:00:00Z from PROFILING"
  for exp in $CORPUS/*.expected; do
    echo "fp-type-rip:$(sed -n 's/^type_rip=\(.\{16\}\).*/\1/p' $exp) PROF-1"
  done; } > profiling/inputs/skiplist
```

Work directories staged per arch into `/tmp/prof-{arm64,amd64}` with the
binaries renamed `vmcore-checker-prof` / `vmcore-checker-tiny-prof`,
`inputs/`, `skiplist`, and `run-profiles.sh`.

linux-arm64 matrix (docker):

```sh
docker build -t vmcore-prof profiling/
docker run --rm --platform linux/arm64 -v /tmp/prof-arm64:/prof vmcore-prof \
    sh /prof/run-profiles.sh /prof /prof/results
```

linux-amd64 matrix (remote box; `$LINUX_BOX` is any amd64 host with GNU
time, `$SCRATCH` a writable scratch directory there):

```sh
ssh $LINUX_BOX "mkdir -p $SCRATCH/vmcheck-prof"
tar czf - -C /tmp/prof-amd64 . | ssh $LINUX_BOX \
    "tar xzf - -C $SCRATCH/vmcheck-prof && cd $SCRATCH/vmcheck-prof && sh run-profiles.sh . results"
ssh $LINUX_BOX "tar czf - -C $SCRATCH/vmcheck-prof/results ." | tar xzf - -C profiling/results/linux-amd64/...
```

`run-profiles.sh` internally runs, per input x binary (see the script
for exact redirections):

```sh
/usr/bin/time -v ./BIN --skiplist skiplist --memstats --note OUT.note.json INPUT   # peak RSS + memstats
/usr/bin/time -v ./vmcore-checker-prof --skiplist skiplist --memprofile OUT.heap.pb.gz --note /dev/null INPUT
GODEBUG=gctrace=1 ./vmcore-checker-prof --skiplist skiplist --note /dev/null INPUT
GOGC=25 ...; GOGC=off ...; GOMEMLIMIT=8MiB ...                                     # stock, largest input only
```

pprof analysis and graphs (on the mac; needs graphviz):

```sh
go tool pprof -sample_index=alloc_space -top -nodecount=12 vmcore-checker-prof-linux-arm64 stock-synth-32m.heap.pb.gz
go tool pprof -sample_index=alloc_space -svg -output stock-synth-32m.alloc_space.svg vmcore-checker-prof-linux-arm64 stock-synth-32m.heap.pb.gz
go tool pprof -sample_index=inuse_space -svg -output stock-synth-32m.inuse_space.svg vmcore-checker-prof-linux-arm64 stock-synth-32m.heap.pb.gz
```

TinyGo static allocation-site listing (its substitute for pprof):

```sh
GOOS=linux GOARCH=arm64 tinygo build -opt=z -no-debug -tags memprofile -print-allocs=. -o /dev/null . \
    > profiling/results/tinygo-print-allocs-{baseline,optimized}.txt 2>&1
```

## Baseline results (peak RSS, KB)

| input     | tiny arm64 | tiny amd64 | stock arm64 | stock amd64 |
|-----------|-----------:|-----------:|------------:|------------:|
| real-700k |      3,256 |      3,072 |       8,932 |       7,180 |
| synth-1m  |      4,152 |      4,096 |       8,920 |       5,128 |
| synth-8m  |     24,792 |     31,744 |      27,848 |      24,588 |
| synth-32m |     84,020 |    117,760 |      98,340 |      92,204 |

Peak was ~2.6-3.7x the input. The baseline `alloc_space` profile
(32 MiB input, stock): 133 MB total allocations —

- 34 MB `regexp.(*Regexp).replaceAll` + 20.5 MB `ReplaceAllString`
  (`StripPrefix` copying every line),
- 32 MB `main.run` (`string(raw)` conversion of the read buffer),
- 32 MB `os.readFileContents` (the read itself — unavoidable),
- 6 MB `strings.genSplit` x2 (full-log line slices).

Baseline memstats agreed on the TinyGo side: `TotalAlloc=200 MB`,
`HeapInuse=92 MB` for the 32 MiB input; TinyGo's conservative,
doubling-growth GC makes transient garbage especially costly.

GC probes (stock, synth-32m): `GOGC=25` ~85 MB, `GOMEMLIMIT=8MiB`
~75-80 MB, `GOGC=off` ~145 MB — tuning trimmed the peak somewhat but
could not fix it: most of the peak was simultaneously-live data.

## Optimizations (in crashfp `dmesgcrash`)

1. `StripPrefix`: return a substring (`FindStringIndex` + slice) instead
   of `regexp.ReplaceAllString`'s per-line copy. (-54 MB allocations)
2. `ParseBytes([]byte)`: zero-copy entry point for callers holding the
   file buffer (`unsafe.String`); the checker uses it. (-32 MB)
3. `Parse` rewritten to scan by byte offset: banner/cmdline top-down
   scan and crash-anchor bottom-up scan allocate nothing; only the
   bounded ~202-line crash region is split and prefix-stripped. (-12 MB
   of line-slice headers; the dominant term for short-line logs)
4. The returned `Crash` clones its retained strings so it never pins
   the input buffer (`cloned()`, including the single-line
   `strings.Join` aliasing edge case).

Behavior is byte-identical: golden corpus, all unit tests, new
`TestParseBytes_*` alias tests, and `make verify-tiny` (stock vs tiny
across corpus + fail-open cases) all green under both compilers.

Intermediate measurements (tiny arm64, synth-32m): 84,020 KB baseline →
66,708 KB after (1) → 50,236 KB after (1)+(2) → 33,560 KB after all.

## Optimized results (peak RSS, KB)

| input     | tiny arm64 | tiny amd64 | stock arm64 | stock amd64 |
|-----------|-----------:|-----------:|------------:|------------:|
| real-700k |      1,464 |      1,024 |       6,620 |       5,164 |
| synth-1m  |      1,720 |      1,024 |       6,556 |       5,164 |
| synth-8m  |      8,892 |      8,192 |      12,508 |      12,332 |
| synth-32m |     33,560 |     32,768 |      38,656 |      36,908 |

Peak is now the input buffer + ~1 MB (tiny) / ~4-5 MB (stock runtime).
Optimized memstats (tiny, 32 MiB): `TotalAlloc=33.7 MB` (was 200 MB);
stock `Mallocs` fell from 1,168,671 to 1,092. Wall time for the tiny
binary on 32 MiB: 0.33s → 0.02s. The optimized `alloc_space` profile is
94% `os.readFileContents` — the only remaining allocation is reading
the log, so further reduction would require mmap or a streaming reader;
not worth it at these numbers. GC probes now show no meaningful spread
(GOGC/GOMEMLIMIT within ~1 MB of default), confirming the peak is live
data, so no GC tuning is baked into the binary.

## Postscript: the --stream mode

A follow-up experiment asked how much a line-streaming parser could
save on top of the above. Answer: peak RSS becomes **constant** — the
binary keeps only a 62-line ring buffer and the bounded ~202-line crash
region. Measured with the shipped tiny binary (linux-arm64, GNU time):

| input     | default (KB) | --stream (KB) |
|-----------|-------------:|--------------:|
| real-700k |        1,472 |           832 |
| synth-32m |       33,536 |           704 |

This shipped as `crashfp dmesgcrash.ParseReader` plus the checker's
`--stream` flag (binary cost: ~6 KB on the TinyGo build). The default
stays the whole-file path; `--stream` is for very tight crashkernel
reservations. Equivalence between the modes is enforced three ways:
`TestParseReaderMatchesParse` in crashfp (streaming vs Parse, including
capture-restart edge cases), `TestStreamMatchesDefault` in this repo
(CLI-level, byte-identical notes), and `scripts/verify-tiny.sh`, which
now runs all four combinations (stock/tiny x default/stream) in CI and
at release time.

## Artifacts

Everything under `profiling/results/<platform>/{baseline,optimized}/`:

- `{tiny,stock}-<input>.time` — full GNU `time -v` output (peak RSS)
  with the `-memstats` dump on the same stderr
- `stock-<input>.heap.pb.gz` — Go heap profiles (open with
  `go tool pprof -sample_index=alloc_space ...`)
- `stock-<input>.{alloc,inuse}_space.svg` + `.top.txt` — rendered graphs
  and top-node listings for real-700k and synth-32m
- `stock-<input>.gctrace` — `GODEBUG=gctrace=1` logs
- `stock-gogc-*`/`stock-gomemlimit-*` — GC tuning probe runs
- `tinygo-print-allocs-{baseline,optimized}.txt` — TinyGo static
  allocation-site reports
- `*.note.json`, `*.stdout` — outputs proving each run took the full
  match + note path

Inputs are not committed; regenerate with `profiling/gen-input.sh`.
